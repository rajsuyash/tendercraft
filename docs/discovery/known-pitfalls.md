# Discovery & Traceability — known pitfalls

Read before writing code; append when you hit a new one. `docs/known-pitfalls.md` applies in full — everything there about Supabase, RLS, cursors, latency, containers and the AI pipeline is live on this surface too. Below is what is specific to Modules F and G.

Format: **symptom → cause → fix.**

## Seeded from the base repo's scars (these will recur here)

- Adapters fetching with a bare `httpx.get()` → new TCP+TLS handshake per call, and worse, the SSRF hop-resolution controls skipped entirely → one pooled, guarded fetcher; the guardrail script fails the build on a direct HTTP import in `sources/`.
- `follow_redirects=True` on a portal fetch → re-enables the redirect-to-metadata bypass → keep it `False`, re-validate every hop. Discovery multiplies untrusted URLs by orders of magnitude; this is the surface where a dormant SSRF hole gets found.
- A cursor on a non-unique column → a bulk source poll gives every row the same insert timestamp, so `created_at < cursor` skips the rest of the page → cursor on the full `(created_at, id)` tuple, emitted with a `Z` suffix.
- New tables without `tenant_id` + RLS + an isolation test → cross-workspace reads. The feed, rules and matrix rows are all workspace-scoped. A consultant seeing client A's shortlist inside client B is ET-6, Sev-1.
- Four counters describing the same object will disagree → one `coverage()` function feeding matrix, export gate and dashboard (G-FR7).
- A UI array mirroring a server enum will drift → rule operators and matrix statuses are closed sets; if the UI lists them, say so in a comment at both ends.

## Hit for real (GeM connector, phase 1)

- **A byte cap that corrupts every compressed response** → `httpx`'s `iter_bytes()` yields *decoded* bytes, so rebuilding a capped `Response` with the original headers leaves `content-encoding: gzip` describing a body that is no longer gzipped. httpx then gunzips it again and raises `DecodingError: incorrect header check` **on the very first fetch** → strip `content-encoding` and `content-length` when rebuilding, or read `iter_raw()` instead. Why this one is worth writing down: it presented as *"the portal is failing"*, pointing away from our own code, and no unit test caught it because the mistake only exists against a server that actually compresses. The first live sweep found it. Cap decoded bytes, not raw — a small gzip bomb should still be refused on its expanded size.
- **GeM's `/all-bids-data` needs a cookie; `/showbidDocument/<id>` does not.** Assuming one posture for a whole portal is wrong: acquisition rules are per-endpoint. Measured 2026-07-30, recorded in `source-gem.md`.
- **The bid document lives under the PARENT bid id (`b_id_parent`), not the item id (`b_id`).** Using the item id returns HTTP 200 with *a different bid's* PDF — no error, no signal, just quietly wrong eligibility on the wrong tender. Pinned by a test because it is otherwise unobservable in production.
- **A clean `assert_no_bot_challenge` is not permission to automate a page.** `_CHALLENGE_MARKERS` (`fetch.py:66-78`) lists the commercial bot-defence vendors — Cloudflare, Imperva, Distil, reCAPTCHA, hCaptcha — because it was written to detect *a portal turning defensive mid-sweep*. It knows nothing about a portal's **own** captcha: `gem.gov.in/view_contracts` gates both its search forms on `captcha_entered` / `h_captcha` / `encryptCaptcha` and the check returned clean (probed 2026-08-07, `source-gem-contracts.md`). Had a connector been built on that clean result it would have POSTed a blank captcha field and recorded the empty response as *"no contracts found"* — a silent, permanent, plausible zero. **Fix:** add the generic markers, and treat "is this surface automatable" as a question for a human source review, never for a runtime check.
- **Acquisition posture is per-endpoint, and the difference between a session and a captcha is the whole rule.** `/all-bids-data` needs an anonymous cookie from a public page — not a credential, so G-8 permits it (`source-gem.md` finding 2). `/view_contracts` needs a solved captcha — an explicit statement by the portal that the surface is for humans, so G-8 refuses it. They are one hostname apart and they resolve opposite ways. Re-review per endpoint; never generalise a verdict across a portal.
- **`ba_official_details_deptName` is literally `"NA"` when absent**, not null. Rendered naively, the feed shows "Ministry of Labour and Employment · NA" as the buying authority.
- **`b_category_name` is truncated mid-word** (`…Petha,Bittergou`); `bd_category_name` carries the full list. Fall back between them, never concatenate.
- **GeM answers an unknown document id with `200`, `content-type: application/pdf`, and a ZERO-BYTE body.** No 404. So a wrong id presents as "the parser found no eligibility fields", which reads as a template change and sends you to the wrong file → assert the body starts with `%PDF` before parsing. This is how the parent-vs-item id mistake above actually surfaced.

## Hit for real (GeM eligibility parser, phase 2)

The bid document is a `wkhtmltopdf`-generated form, which makes the eligibility subset a parse rather than a model extraction. Everything below is a way that parse silently returns the wrong thing.

- **`pypdf`'s default `extract_text()` separates every label from its value**, so `Minimum Average Annual Turnover` arrives with no number attached and the parser reports "field absent" on a document that plainly states it → `extract_text(extraction_mode="layout")`. (`pdftotext -layout` works too but adds a poppler system binary for no extra capability.) The parser depends entirely on label and value sharing a line.
- **Stripping the mangled Devanagari half of each bilingual label shifts every column left by a different amount per line**, destroying the indentation that identifies a wrapped value → replace non-ASCII with **spaces**, never delete it. Symptom: `Item Category` came back starting mid-sentence at `"testing & Maintaining…"`, having silently dropped its own first line.
- **GeM vertically centres a label against a tall value cell, so a multi-line value begins on lines ABOVE its own label.** Reading only the label line returned GeM's standing exemption boilerplate instead of the actual requested-documents list — authoritative-looking and wrong.
- **EMD and ePBG have two mutually exclusive shapes and only one appears per bid.** Low-value: `/Required  No`. High-value: `/EMD Amount  31200000` and `/ePBG Percentage(%)  5.00`, with **no `/Required` row at all**. Reading only the first shape reported `emd_required: None` on a bid demanding a **₹3.12 crore** deposit — an "unknown" concealing the largest number a bidder needs to find up front. An amount present means required, whatever the Required row says or omits.
- **`/Required` appears twice per document** — under `/EMD Detail` and under `/ePBG Detail` — with identical text. An unbounded scan from the EMD heading finds the *ePBG* row whenever the EMD section has no `/Required` of its own, i.e. on every high-value bid. Both are commonly "No", so it stays invisible until the one bid where they differ, and then it tells a bidder no deposit is needed → bound every section lookup to the next heading.
- **A tri-state is mandatory on every boolean.** `None` (row not found) and `False` (row says No) are different facts; collapsing them tells a bidder they need no bank guarantee when we merely failed to read the row.
- **Unknown magnitude words must be refused, not assumed to be rupees.** `parse_amount("5 Million")` returning `5` would hand a bidder a Likely-eligible they do not have. Lakh = 1e5, Crore = 1e7; anything else → `None`.
- **`Estimated Bid Value` and `Minimum Average Annual Turnover` are genuinely OPTIONAL** — plenty of live bids omit both. Every document does however contain the *sentence* "Estimated Bid Value indicated above is being declared solely for the purpose of guidance on EMD amount…", so a loose regex parses prose into a fact. Anchor on the labelled row (`/`-prefixed), and keep a fixture whose field is truly absent so a regression that returns `None` everywhere cannot look green.

## Hit for real (capability relevance, F-FR11)

- **PostgREST rejects a bulk insert whose objects have DIFFERENT KEYS** with a bare `400 Bad Request` — no column name, no hint, and the engine's envelope turns it into `DB_ERROR: database request failed`. It appears the moment a patch applies to only some rows, which is exactly what ranking does (only in-scope rows get relevance fields) → pad every row to the union of keys before upserting. Cost an hour of looking at the wrong layer.
- **New columns are invisible to PostgREST until its schema cache reloads.** Adding them by SQL succeeds and `information_schema` shows them, while every insert still 400s → `notify pgrst, 'reload schema';`. Check this BEFORE suspecting the payload.
- **A `text` band sorts alphabetically: high, low, medium.** Ranking by it silently puts the worst matches second and reads as "the ranking doesn't work" → make it a Postgres ENUM, whose members sort in declaration order. `create type relevance_band as enum ('high','medium','low')` then `order by relevance_band` is correct for free.
- **Prefix/stem matching needs a length floor, and one floor is not enough.** At 4 characters the keyword `desktop` matched the token `desk` and banded a classroom "Desk and Bench Set" as a top fit for an IT supplier. Raising the floor to 5 then broke category matching, because **GeM's category codes are truncated to four-letter segments** (`home_info_netw`). Two floors: 5 for free text, 4 for category codes and one-directional there (the code may open the vendor's word, never the reverse).
- **Tailwind's `line-clamp-n` needs `display:-webkit-box`, so a `block` beside it silently wins** and the clamp does nothing — a model rationale then renders at full length and a table row grows to 200px. Same class of bug as any two utilities setting the same property.
- **`whitespace-nowrap` on a chip inside a `table-fixed` layout overflows the whole table**, not just the cell. The verdict chip "CLEARS TURNOVER BAR" pushed the last column past the viewport edge.
- **`exclude_none=True` on the profile update means a field can never be cleared** (`analyze_routes.py`): sending `null` is silently dropped rather than written. Send `""` for text. An array is never `None`, so it round-trips normally — but it is therefore written on every save and must always be populated from form state.

## Anticipated, specific to this surface

- **A broken adapter renders as an empty feed, not as an error.** The portal changed its markup, the parser returns zero rows, and the feed simply looks quiet. Nobody notices for six weeks, and the product's single most valuable promise is silently false the whole time → item-count deviation vs. the trailing median is an **incident** (EC-8); the feed carries a per-source coverage banner naming any degraded source and its last successful fetch. **A zero from a source that has never returned zero is a bug until proven otherwise.**
- **Dedup tuned on precision quietly deletes tenders.** Fuzzy merging looks great in a demo — fewer duplicates, tidier feed — and every wrong merge removes a real tender with no error message anywhere. → merge on exact normalized `portal_ref_no` only; near-matches group as a suggestion. FIX-7 carries a deliberate near-miss pair (same authority, same closing date, different tender); if it ever merges, the gate is broken.
- **A model filling a `null` field defeats G-9 through the back door.** An adapter that asks a model to guess `estimated_value` gives model output the power to move an item past a value-band rule — the exclusion path becomes model-driven without a single line that looks like exclusion → `null` stays `null`; deterministic rules must treat `null` as "does not match an exclusion", never as "excluded".
- **A relevance score rendered as a decimal will be believed.** 0.62 implies a calibration this signal does not have, and users will build rules on it → bands only, with the cited past project that produced the band.
- **Depth-1 eligibility labels will be treated as verdicts.** They are provisional by construction, computed from a listing record and a partial NIT → label the depth in the DOM (`[data-triage-depth]`), never let Depth-1 feed a Bid/No-Bid card, and rank `Likely ineligible` items down rather than hiding them (C-FR9).
- **The daily digest becomes the new thing nobody reads.** A feed at 300 items/day is exactly the Excel tracker it replaced → in-scope volume is a gate (F-AC2, ≤ 25/day), and rule tuning is part of onboarding, not a settings page the user finds later.
- **Triage cost scales with the feed, not with bids.** Running an extractor over every NIT for every workspace is the cost blowup this module can produce → the escalation ladder in product PRD §4.1 is deterministic and capped; log cost per workspace-day and render it in settings before the bill teaches you.
- **An aggregator digest email parsed as one tender loses nine.** Forwarded digests contain many tenders in one message → parse into individual opportunities where structure permits; where it does not, flag for manual split and **never drop the email** (EC-10).
- **Requirement sentences hide in table cells, footnotes and annexure references.** A shredder tuned on prose silently under-counts, and the unmapped denominator — the whole point of G-FR2 — reports a comfortable zero → FIX-10 plants one of each; an unresolvable structure is listed for human resolution, never dropped.
- **A re-imported spreadsheet rewriting the locked TOM.** Someone edits a requirement cell in Excel to "clarify" it, re-imports, and the locked tender model — the artifact everything downstream trusts — changes without passing the lock gate → requirement text, level and anchor are import-protected; an edit there is a conflict, not a merge.
- **An answer reused from a losing bid, presented without that context.** Reuse without outcome linkage propagates whatever lost → suggestions carry the source bid, its date, and its outcome where known.
- **A template-marker document reaching the answer library.** Already learned on the bidder side: an unfilled template ("[Insert Designation]") cited into a proposal looks *sourced*. The answer library is a second doorway into the same failure → run the existing template-marker detection on anything entering it.
